# 제품 요약 프롬프트 (product.summary / product.composition_text)

제품 하나의 전성분 구성을 종합해서, 카드 앞면 "한 줄 요약"과 "성분 구성을 살펴보면" 본문
두 개를 만든다. `product.summary`(one_liner)와 `product.composition_text`는 DB에서도
별도 컬럼이다 — 하나로 합치지 않는다.

## 입력 (아래 JSON 그대로 프롬프트에 삽입됨 — `scripts/build_llm_input.py` 참고)

```
{input_json}
```

입력 필드 설명:
- `key_ingredients`: DB 큐레이션 핵심 성분(`product.key_ingredients`) 각각의 이름 + 대표 배합목적
  + `label_rank`(전성분표 순서, 1이 가장 앞/고농도 추정) + `matched_text`(라벨 원문, 함량이
  적혀 있으면 그대로 포함— 예: "소듐디엔에이(100ppm)"). `one_liner`/`composition_text` 둘 다
  이 목록이 가장 중요한 근거다.
  - `label_rank`가 `total_ingredient_count`의 뒤쪽 절반을 넘거나 `matched_text`의 함량이
    낮으면(예: 1% 미만으로 보이는 ppm 단위) 그 성분은 소량 배합된 것으로 보고, "듬뿍 함유돼
    있다"는 식으로 과장하지 말고 "소량 배합돼 있다/함유 자체에 의미가 있다"처럼 담백하게
    표현한다. 반대로 앞쪽 순위면 비중 있게 써도 된다. **화장품법상 1% 미만 성분은 순서
    상관없이 뒤쪽 아무 데나 적을 수 있어 label_rank가 뒤쪽이라고 무조건 미량이 확정된 건
    아니다** — "~일 가능성이 있다/~에 가깝다" 정도의 추정 톤을 쓰고, 확정적으로 단정하지 않는다.
- `category_description`: `app/product_category.py`가 제품 카테고리(스킨/토너 → 세럼/에센스/
  앰플 → 크림)로부터 만든 스킨케어 순서 고정 문구(LLM 아님, DB). "스킨케어 순서" 얘기를 할 땐
  반드시 이 문구를 근거로만 쓴다 — 이 문구에 없는 순서(예: "아이크림 다음에", "자외선차단제
  전에" 같은 구체적 디테일)는 지어내지 않는다. 카테고리가 미분류라 빈 문자열이면 스킨케어
  순서 언급 자체를 하지 않는다.
- `total_ingredient_count`: 전성분 총 개수 — `label_rank`가 상대적으로 앞/뒤 어디쯤인지
  판단할 때 쓴다(예: "39개 중 35번째"면 뒤쪽으로 판단).
- `product_concern`: 이 제품이 겨냥하는 피부고민 태그(화면엔 아직 안 나오는 데이터). 요약에
  자연스럽게 녹일 수 있으면 반영하되, 이 배열에 없는 고민을 지어내지 않는다.
- `key_ingredient_relations`: `key_ingredients` 사이에 실제로 걸려 있는 시너지/악화 조합(DB
  `ingredient_relation`). 있으면 "성분 구성을 살펴보면"에서 왜 같이 쓰였는지 근거로 쓸 수 있다.
  비어 있으면 조합 관련 언급을 하지 않는다.

## 출력 — 아래 키를 가진 JSON 객체 하나만 출력한다 (그 외 텍스트 절대 금지)

```json
{
  "one_liner": "",
  "composition_text": ""
}
```

- `one_liner`: 전체 성분 구성을 함축한 자연스러운 문장 하나(카드 맨 위, 가장 크게 노출됨).
  성분명을 나열하지 않는다 — `key_ingredients`가 왜 배합됐는지의 "결론"만 한 문장으로.
  마크다운 볼드는 여기엔 쓰지 않는다(아래 4번 참고 — 볼드는 composition_text 전용).
- `composition_text`: `key_ingredients`(+ 있으면 `key_ingredient_relations`)를 근거로,
  `one_liner`를 왜 그렇게 요약했는지 3~5문장으로 풀어 설명한다. `one_liner` 문장을 그대로
  반복하지 않는다. 화장품 성분 전문가가 일반 소비자에게 설명하듯, 각 핵심 성분이 구체적으로
  어떤 역할을 하는지(예: "여러 히알루론산 유도체가 겹겹이 쌓여 수분을 채우고") 풀어 쓴다.
  - **스킨케어 순서를 이 문단 안에 자연스럽게 포함한다** — `category_description`이 있으면
    그 내용을 문장 하나로 녹여 넣는다(예: "가벼운 세럼이라 토너 다음, 크림 전에 발라주면
    좋아요"). 별도 섹션이 아니라 이 문단의 마지막 문장 정도로 붙인다. `category_description`이
    빈 문자열이면 스킨케어 순서 언급을 아예 하지 않는다(지어내지 않음).
  - 위 `label_rank`/`matched_text` 근거로 미량 배합이 의심되는 성분은 담백하게(예: "함유
    자체에 의미를 두면 좋아요") 표현하고, 효과를 과장하지 않는다.

## 출력 형식 — 마크다운 볼드 (반드시 지킬 것)
`composition_text` 문단 안에서 **아래 두 가지는 반드시 볼드로 감싼다** — 제품명은 절대
볼드로 감싸지 않는다(제품명은 이미 카드 위쪽에 크게 나와 있어서 여기서 또 강조할 필요가 없다):

1. **`key_ingredients`에 있는 성분명 각각** — 문단에서 그 성분을 처음 언급하는 자리에
   `**성분명**`으로 감싼다. `key_ingredients`가 5개면 문단 안에서 최소 3개 이상은 볼드로
   언급돼야 한다(전부 다룰 필요는 없지만, 언급하는 성분은 반드시 볼드).
2. **스킨케어 순서 어구** — `category_description`을 근거로 넣은 문장에서, 시점을 나타내는
   핵심 어구만 볼드로 감싼다(문장 전체를 감싸지 않는다). 예: "**토너 다음, 크림 전에** 발라
   주면 좋아요"에서 볼드 부분만.

예시(형식만 참고, 내용은 실제 입력 데이터로 새로 써야 함):
`"**소듐하이알루로네이트**를 비롯한 여러 히알루론산 유도체가 겹겹이 쌓여 수분을 채우고,
**나이아신아마이드**가 피부 톤을 관리해요. **판테놀**은 보습을 보완하고요. 가벼운
제형이라 **토너 다음, 크림 전에** 사용하면 좋아요."`

프론트가 `**...**`를 파싱해서 굵게 렌더링한다 — 그 외 마크다운(제목, 목록, 코드블록 등)은
쓰지 않는다.

## 규칙
1. 톤: "~이에요/~해요" 체, 쉬운 말이면서도 성분 전문가답게 구체적으로.
2. 사실만 — `key_ingredients`/`product_concern`/`key_ingredient_relations`/`category_description`에
   없는 성분·효능·고민·궁합·스킨케어 순서 디테일은 절대 만들어내지 않는다. `label_rank`/
   `matched_text` 기반의 미량 여부 판단도 추정 톤을 쓰고 단정하지 않는다(위 참고).
3. 광고 문구처럼 과장하지 않는다. "치료", "완치", "예방효과", "100% 안전", "부작용 없음" 금지.
4. 출력은 JSON 객체 하나만. 마크다운 코드펜스, 설명, 인사말 등 그 외 텍스트를 절대 붙이지 않는다
   (단, `composition_text` 값 내부의 `**볼드**`는 허용 — 위 "출력 형식" 참고).
5. JSON 파싱에 실패할 응답을 만들지 않는다 — 호출부는 파싱 실패 시 재시도 없이 폐기하고
   두 필드 모두 빈 값으로 둔다.

## 지금 바로 실행

위 "입력" 섹션의 JSON은 예시가 아니라 **지금 실제로 주어진 데이터**다. 사용자가 추가로 입력을
보내지 않는다 — 되묻거나, 앞으로 어떻게 할지 설명하거나, 확인을 요청하지 마라. 지금 이 데이터를
그대로 사용해서 결과 JSON 객체 하나만 즉시 출력해라.
