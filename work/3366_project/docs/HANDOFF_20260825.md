## 1. 프로젝트 목적

**LabelLens**: 화장품 라벨(전성분표)을 분석해 사용자에게 다음을 보여주는 서비스.
- 핵심 성분·효능, 배합목적
- 피부 타입별(지성/복합성/건성/민감성) 위험/궁합 성분
- 비슷한 제품 추천
- 성분/제품에 대한 LLM 생성 설명(쉬운 말 요약)

구성:
- **백엔드**: `work/3366_project/` — FastAPI + PostgreSQL(운영) / SQLite(`data/labellens.db`, 마이그레이션
  원본이자 git 추적 백업)
- **프론트엔드**: `work/frontend/` — React + Vite, 검색→결과 카드 뒤집기 UI
- **최종 목표**(README 기준): 성분표 사진 OCR → 성분 매칭 → LLM 쉬운 설명까지 한 번에 되는 서비스.
  OCR은 이미 붙어 있고(PaddleOCR), 이번 작업은 그중 **"LLM 쉬운 설명" 파이프라인을 Ollama/gemma에서
  vLLM/Qwen으로 옮기고, 지정된 9개 제품에 대해 실제로 캐시를 채우는 것**이었다.

## 2. 완료된 작업 (이 세션에서 한 일만 — 아래 6번 "주요 의사결정" 참고)

### 2-1. `caution_group_text` 필드를 실제 생성 파이프라인에 연결
- `LLMSummary` 모델/스키마/프론트 타입에는 이미 존재했지만, 프롬프트와 생성 스크립트가 6개 필드 중
  5개만 다뤘다(`caution_group_text` 누락). 근거 데이터(`ingredient_skin_score.is_risk`)는 이미
  `build_llm_input.py`가 프롬프트에 넘기고 있었는데 출력 스키마에서 안 쓰이고 있었다.
- **수정 파일**:
  - `prompts/ingredient_summary.md` — 출력 JSON에 `caution_group_text` 추가, `skin_scores`에
    `is_risk: true` 항목이 있을 때만 채우도록 규칙 명시.
  - `scripts/generate_llm_summaries.py` — `LLM_SUMMARY_FIELDS` 리스트에 `caution_group_text` 추가.

### 2-2. 지정 9개 제품 전성분 LLM 요약 생성·캐싱 — **완료, 실패 0건**
- **신규 파일**: `scripts/generate_target_products.py`
  - 대상 제품의 **전성분 전체**(product_ingredient 전체, 큐레이션된 `key_ingredients` 5개가 아님)를
    돈다. 여러 제품에 겹치는 성분(나이아신아마이드, 글리세린 등)은 한 번만 생성하고 재사용.
  - 이미 채워진 성분(`llm_summary.summary_text` non-empty)/제품(`summary`+`composition_text` 둘 다
    non-empty)은 LLM 호출 없이 skip.
  - **코드 레벨 근거 강제(enforce_evidence_gates)**: LLM이 프롬프트 규칙을 안 지켜도, `safety_level`
    없으면 `caution_text`, `relations` 없으면 `combo_recommendation`, `is_risk` 성분 없으면
    `caution_group_text`를 무조건 빈 문자열로 덮어쓴다.
  - 성분/제품 단위 UPSERT + commit 개별 처리, 실패해도 rollback 후 계속 진행.
  - 로그: `logs/generate_target_products_YYYYMMDD_HHMMSS.log` (진행 로그, 파일로 남음),
    `..._failures.json` (실패 목록, 이번엔 빈 배열).
- **결과**: 9개 제품 전성분 305개(중복 제외 고유 성분 기준 아님 — 제품별 product_ingredient 행 수
  합계) 전부 `llm_summary.summary_text` 채워짐, 제품 요약(`summary`+`composition_text`)도 9개 전부
  채워짐. 실패 0건. (아래 5번 "현재 진행 상태"에 상세 표.)

### 2-3. vLLM 서버를 max-model-len 40960으로 재기동

### vLLM 재기동 명령 (필요 시 참고)
```bash
source /tmp/vgpu/venv-vllm/bin/activate   # ninja 등 PATH에 잡히려면 필수 — 활성화 안 하면 flashinfer JIT 컴파일 단계에서 죽음

  --gpu-memory-utilization 0.85 --enforce-eager --port 8000 --host 127.0.0.1
```

- GPU: A100-PCIE-40GB 이지만 **HAMI vGPU 슬라이스로 가상화되어 이 컨테이너에서는 총 15258MiB(≈14.9GB)만

  메모리 설정 안 바꿔도 됨. 47,808 넘기려면 `--gpu-memory-utilization`도 같이 올려야 함(OOM 위험 검토 필요).

## 7. 주요 의사결정

- **`caution_group_text`의 의미를 `ingredient_skin_score.is_risk` 데이터로 정의함** — DB 스키마/문서엔
  "주의 그룹 라벨"이라고만 적혀 있고 정확한 정의가 없었다. `caution_text`(safety_level 근거, 대부분
  비어있음 — 전체 성분 중 5개만 safety_level 있음)와 겹치지 않으면서 실제로 쓸 수 있는 근거 데이터가
  `ingredient_skin_score`(is_risk=true 21건)뿐이라 이걸로 정의했다. **다른 의미를 의도했을 수 있으니
  실제 화면에 노출하기 전에 재확인 권장** — 지금은 어느 컴포넌트에도 `caution_group_text`가 렌더링되고
  있지 않다(확인함, 안전한 상태).
- **키 성분(`key_ingredients`, 5개) 대신 전성분 전체를 생성 대상으로 함** — 사용자 요청이 "그 상품과
  성분들에 대해"였고, 전성분 목록(카드 뒷면)도 화면에 노출되는 데이터라 부분만 채우면 UI 일부가 빈
  채로 남기 때문.
- **제품 간 겹치는 성분은 한 번만 생성(전역 dedup)** — 나이아신아마이드처럼 9개 중 여러 제품에
  들어가는 성분이 많아서, 안 그러면 같은 성분을 여러 번 재생성(다른 문구로) 하게 됨. 대신
  "어느 제품 맥락으로 생성했는지"는 첫 번째로 만난 제품 기준 — 성분 설명 자체가 제품 특정적이지 않게
  나오도록 프롬프트가 이미 유도하고 있어서 실질적 영향은 적다고 판단.
- **필드별 근거 게이트를 프롬프트뿐 아니라 코드로도 강제** — LLM이 "근거 없으면 빈 문자열" 규칙을
  안 지킬 가능성을 신뢰하지 않고, `enforce_evidence_gates()`로 후처리 검증을 추가함. (사용자의
  "근거 밖 지어내기 금지" 요구사항을 코드 레벨로 보강.)
- **max-model-len을 4096→40960으로 올릴 때 `--gpu-memory-utilization`은 그대로 둠** — 이전 세션의
  vLLM 시도 로그(`vllm-serve3.log`)에서 KV 캐시 풀이 47,808 토큰으로 계산되는 걸 확인했고, 이게
  40,960보다 크므로 별도 메모리 설정 변경 없이 안전하다고 판단(실제로 기동 성공, 로그의
  "Maximum concurrency for 40,960 tokens per request: 1.17x"로 확인).
- **`gemma-4-26B-A4B-it-AWQ-4bit` 교체는 진행 전에 사용자에게 확인받음** — 가중치 크기(17.2GB)가
  GPU 슬라이스 총 용량(14.9GB)을 넘어서는 게 명백해서, 실패가 거의 확실한 작업(모델 다운로드 포함)을
  먼저 실행하지 않고 사용자 판단을 물었다.
- **버려진 대안**: `scripts/generate_llm_summaries.py`의 기존 `--key-ingredients` 플래그를 그대로
  써서 5개 핵심 성분만 생성하는 방법은 채택 안 함 (위 "전성분 전체" 결정 참고). `nohup ... &` 배경
  실행 방식도 실패 경험 후 버림(위 6번 문제#1).
