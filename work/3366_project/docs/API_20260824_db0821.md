# LabelLens API 명세

이 문서는 **추측이 아니라 실제 코드(`app/routers/*.py`, `app/schemas/*.py`)와 실제 DB(`data/labellens.db`),
그리고 로컬에서 실제로 뜬 응답**을 근거로 작성했습니다. 실제와 다르거나 아직 없는 부분은 "❌ 미구현"으로
명시했습니다.

- 로컬 개발 서버: `http://127.0.0.1:8000` (`uvicorn app.main:app`, SQLite `data/labellens.db` 기준)
- 응답 예시 기준 제품: **아누아 피디알엔 히알루론산 캡슐 100 세럼 30mL** (`product_id=p-69250fe7725a`)
- 캡처 시각: 이 문서 작성 시점, `GET /products/p-69250fe7725a` 실응답 그대로 첨부 (3번 항목)

## ⚠️ 2026-08-24 GitLab backendOcr 브랜치 업데이트 병합 반영

백엔드/DB/스키마가 아래처럼 바뀌었습니다 (이 문서는 병합 이후 기준으로 갱신됨):

- `key_ingredients_raw`(콤마 문자열) → **`key_ingredients`**(JSON 배열, `app/core_ingredient_selector.py`가
  재계산 — 원본 큐레이션 값과 다를 수 있음)
- 기존 계산 필드 `key_ingredients`(label_rank 상위 N개) → **`top_ingredients`**로 개명 (이름 충돌 회피)
- 신규 필드: `product.skin_score_summary`(문장 요약), `app/search_service.py` 기반 토큰 검색
- `GET /products/{id}/skin-fit`: "0~100 적합도 점수" 방식 폐기 → **위험 성분 탐지**(`SkinRiskRead`) 방식으로 전면 개편
- DB 교체: 제품 111→144개, `ingredient_skin_score`는 점수(-3~+3) 228행 → 위험 플래그(`is_risk`) 42행으로 재구성
- `relations`(시너지/악화)와 `composition_text`는 병합 후에도 유지됨 (재통합 완료)

## ⚠️ 지금 상태: LLM(Qwen) 미연결

아래 필드들은 **아직 실제 LLM 호출 없이 임시 텍스트로 채워지고 있습니다** (자세한 출처는 각 표의
"LLM(임시)" 표시 참고):

- `ingredient.llm_summary.summary_text` — LLM_SUMMARY에 값이 있으면 그대로, 없으면 `ingredient.summary`
  (성분 정의 원문)로 폴백.
- `ingredient.llm_summary.benefit_text` / `usage_reason_text` / `caution_group_text` / `combo_recommendation`
  — DB에 값이 있으면 그대로(과거 배치로 채워진 값), 없으면 빈 문자열.
- `product.summary`(one_liner) / `product.composition_text` — 대부분 `null`.

Qwen이 실제로 붙으면 `app/llm_client.py`(`prompts/ingredient_summary.md`, `prompts/product_summary.md`
템플릿 참고)가 이 값들을 실제 생성 텍스트로 교체합니다. **API 응답의 필드명·구조는 바뀌지 않습니다** —
값의 출처만 "임시/DB 폴백"에서 "LLM 생성"으로 바뀝니다.

## 2. 응답 필드별 출처 — `GET /products/{product_id}` (성분 요약 페이지 메인 엔드포인트)

범례: **DB**=DB에서 읽어 그대로 · **LLM**=LLM 생성 대상 필드(지금은 임시/폴백) · **LLM(조건부)**=조건
있을 때만 채워짐 · **계산**=코드가 다른 값으로부터 계산 · ❌=이 응답에 없음(별도 엔드포인트 또는 미구현)

### 제품 레벨 (`ProductDetail`, `app/schemas/product.py`)

| 필드 | 타입 | 설명 | 출처 |
|---|---|---|---|
| `product_id` | str | `p-`+uuid12 | DB (`product.product_id`) |
| `product_name` | str | 제품명 | DB |
| `brand` | str\|null | 브랜드 | DB |
| `category` | str\|null | 카테고리 (`app/product_category.py`가 제품명으로 자동분류해 저장한 값) | DB |
| `summary` | str\|null | **카드 상단 "한 줄 요약"(one_liner)** | **LLM** (지금 대부분 `null`) |
| `composition_text` | str\|null | **"성분 구성을 살펴보면" 본문** | **LLM** (지금 전부 `null`) |
| `summary_generated_at` | datetime\|null | 위 두 필드 생성 시각 | DB (LLM 생성 시 기록) |
| `skin_score_summary` | str | 위험 성분 매칭 요약 문장 (예: `"건성에 유의해야할 성분 1개 있습니다."`) | 계산 (`app/skin_fit.py summarize_skin_score_matches`, 매칭 없으면 `"..."`) |
| `key_ingredients` | list[str] | **DB에 JSON 배열 문자열로 저장된 핵심 성분명 5개** — `app/core_ingredient_selector.py`가 배합목적표+전성분으로 재계산한 값(`scripts/backfill_key_ingredients.py`로 채움). 응답 시점에 문자열→배열로 파싱됨(`ProductRead._parse_json_list`) | DB (`product.key_ingredients` 컬럼) |
| `key_purposes` | list[str] | 위와 같은 방식의 핵심 배합목적(최대 5개, 중복 제거) | DB (`product.key_purposes` 컬럼) |
| `oliveyoung_url` | str | 올리브영 검색 링크 | 계산 (product_name으로 그때그때 생성, 저장 안 됨) |
| `category_order` | int | 스킨케어 루틴 순서(1=토너,2=세럼,3=크림,99=기타) | 계산 (`category` 기반) |
| `category_description` | str | 카테고리 사용 안내 문구 | 계산 (`category` 기반 고정 문구) |
| `ingredients` | array | 전성분 목록 (아래 "성분 레벨" 표) | - |
| `top_ingredients` | array | **핵심 성분 카드용** — `ingredients`를 `label_rank` 상위 `DEFAULT_TOP_K`(5, `app/similarity.py`)개로 자른 것 | 계산 (⚠️ `key_ingredients`와 이름은 다르지만 **개념도 다른 값** — 아래 참고) |
| `similar_products` | array | 유사 제품 추천 (`{product: ProductRead, score: float}`) | 계산 (`app/similarity.py` — `key_ingredients` 자카드 유사도 70% + 나머지 성분 30%) |

⚠️ **`top_ingredients`(label_rank 상위 N개) vs `key_ingredients`(core_ingredient_selector 재계산)는
서로 다른 개념입니다.** 예전엔 `key_ingredients`라는 이름을 계산값이 썼는데, 병합 후 DB 컬럼과
이름이 겹쳐서 계산값 쪽을 `top_ingredients`로 개명했습니다. 아누아 세럼 기준: `key_ingredients`(DB,
core_ingredient_selector)는 `하이드롤라이즈드하이알루로닉애씨드,나이아신아마이드,하이드롤라이즈드콜라겐,
소듐하이알루로네이트,아데노신`이고, `top_ingredients`(label_rank 1~5위)도 우연히 아누아 세럼에서는
**같은 5개**로 나옵니다 — 하지만 산출 근거가 다르므로(전자는 정제수·용제 등을 걸러내는 알고리즘, 후자는
단순 배합순서) 다른 제품에서는 갈릴 수 있습니다. 화면의 "핵심 성분" 카드 그리드는 `top_ingredients`를
쓰고, "핵심/일반 배지"는 `key_ingredients`(문자열 배열)와 `ingredient.name_kr`을 대조해서 정합니다
(프론트 `api.ts`).

❌ **미구현**: `product_concern`(피부고민 태그) — DB엔 테이블이 있지만 이 응답에도, 다른 어떤 엔드포인트
에도 노출되지 않습니다. 지금은 `scripts/build_llm_input.py`가 DB를 직접 조회해 LLM 프롬프트 근거로만
씁니다.

### 성분 레벨 (`ProductIngredientDetail` — `ingredients[]`, `top_ingredients[]` 배열의 원소)

| 필드 | 타입 | 설명 | 출처 |
|---|---|---|---|
| `label_rank` | int\|null | 라벨 표기 순서(=농도 순, 1이 최다) | DB (`product_ingredient.label_rank`) |

`product.key_ingredients`(문자열 배열)와 `ingredient.name_kr`을 대조해서 판정합니다

### `GET /products/{id}/skin-fit` 응답 (`SkinRiskRead`, `app/schemas/skin_fit.py`)

⚠️ **2026-08-21 설계 전면 개편**: "-3~+3 적합도 점수를 합산해 0~100점" 방식을 폐기했습니다 — 점수
자체가 근거 없는 가짜 정밀도였다는 판단(`app/skin_fit.py` 상단 주석 참고). 지금은 "위험 성분이 있는지
여부"만 알려주는 훨씬 단순한 구조입니다. 긍정적 점수(좋은 성분)는 더 이상 다루지 않습니다.

| 필드 | 타입 | 설명 | 출처 |
|---|---|---|---|

## 4. 화면 영역 ↔ 필드 매핑 (성분 요약 페이지, `work/frontend/src/components/Result*.tsx`)

| 화면 영역 | 컴포넌트 | 필드 | 출처 |
|---|---|---|---|
| 상단 한 줄 요약 (따옴표 문구) | `ResultSummaryPanel` | `product.summary` | **LLM** (지금 `null` → 프론트에서 빈 문자열) |
| 핵심 성분 카드(칩) | `ResultSummaryPanel` | `product.top_ingredients[].ingredient.name_kr` + 라벨(`purposes`에서 추출) | **DB** |
| 핵심/일반 배지 | `IngredientRow`/`IngredientDetail` | `product.key_ingredients`(문자열 배열)에 `ingredient.name_kr` 포함 여부 | **DB** (프론트 파생 판정) |
| "성분 구성을 살펴보면" 본문 | `ResultSummaryPanel` | `product.composition_text` | **LLM** (지금 `null`) |
| 사용 전 확인해 주세요 | `ResultSummaryPanel` | ❌ 대응 필드 없음 | ❌ 미구현 (규제/한도 데이터 없음 — 항상 빈 배열) |
| 전성분 목록 한 줄(배합 이유) | `IngredientRow` | `ingredient.llm_summary.usage_reason_text` | **LLM** (비어있으면 프론트가 `purposes`로 `"○○ 목적으로 배합."` 문구 폴백) |
| 성분 상세 — 안전 등급 | `IngredientDetail` | `ingredient.safety_level` | **DB** (⚠️ 지금 전부 `null` → 프론트 `"일반"` 기본값) |
| 성분 상세 — 상세설명 | `IngredientDetail` | `ingredient.llm_summary.summary_text` | **LLM** (없으면 `ingredient.summary` 원문 폴백) |
| 성분 상세 — 좋은 점 | `IngredientDetail` | `ingredient.llm_summary.benefit_text` | **LLM** |
| 성분 상세 — 나쁜 점 | `IngredientDetail` | `ingredient.llm_summary.caution_text` | **LLM(조건부)** — `safety_level` 있을 때만 |
| 성분 상세 — 배합목적 | `IngredientDetail` | `ingredient.purposes[]` | **DB** |
| 성분 상세 — 다른 성분과의 궁합(목록) | `IngredientDetail` | `relations[]` | **DB** |
| 성분 상세 — 궁합 팁(문장) | `IngredientDetail` | `ingredient.llm_summary.combo_recommendation` | **LLM(조건부)** — `relations` 있을 때만 |

## 5. 아직 API에 없는 것 (DB엔 있지만 미노출, 또는 완전 미구현)

| 항목 | DB 존재 | API 노출 | 비고 |
|---|---|---|---|
| `product_concern`(피부고민 태그) | ✅ | ❌ | 어떤 엔드포인트에도 없음. LLM 프롬프트 근거로만 DB 직접 조회(`scripts/build_llm_input.py`) |
